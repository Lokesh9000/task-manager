# PA 5 Retrospective

## 1. Plan Mode value

The amendment that mattered most was in Session 1 of `PLAN_LOG.md`. The original plan (`plans/session1-original-plan.md`) added tests that call `create_task()`, which writes into the module-level `TASKS` dictionary in `services/tasks.py`, and its only protection against tests affecting each other was that the new tests would not assert on fixed task IDs. I did not approve that. I asked for a `restore_tasks` fixture that takes a deep-copy snapshot of `TASKS` and restores it in `finally`, applied to every new test that mutates `TASKS`. I also asked that results not depend on execution order and that the expected test count be checked, and the amended plan (`plans/session1-amended-plan.md`) added a reverse-order run for that. The result was 16 passed in both normal and reverse order. I think this prevented a real problem later, not just a tidier test file. Sessions 3 and 4 added tests that compare `TASKS` to a snapshot and, in Session 4, assert that `list_tasks()` returns ids `[1, 2, 3]`. If the Session 1 create tests had left extra tasks behind, those later assertions would have depended on which tests ran first, and I would probably have had to go back and rework the Session 1 tests after two more sessions were built on them. I cannot prove a revert would have been needed, but the later tests only work because the store is clean at the start of each test.

## 2. Plan Mode limits

Session 3 is the case where the output did not fully match the amended plan. The production code matched: the `PATCH /api/tasks/<id>` route in `routes/api.py` and `update_task_priority()` in `services/tasks.py` are what `plans/session3-amended-plan.md` describes, and all 73 tests passed. The tests were different. Four API tests in `tests/test_api.py` were combined, renamed or added compared with the saved plan. When I looked into why, the cause was mine as much as Claude's. I had asked for the amendment in a separate conversation, outside Plan Mode, and saved that reconstructed revision as `plans/session3-amended-plan.md`, but the Plan Mode session that actually implemented the change never read that file. It only received my approval of decisions 1 and 2, revised its own plan, and implemented its own version, which had a different test list. So there were two amended plans, and the one I saved as evidence was not the one that was executed. That session also had to change one test again while implementing, because the Flask test client sends no body for `json=None` and the first run was 1 failed, 72 passed. From this one case, it looks like Plan Mode held for the behavior I reviewed closely, such as the route and its error order, and slipped on details I only skimmed, such as test names and groupings, although a single example cannot show how general that is. It also only governs the session it runs in. A plan saved somewhere else is just a document, and the only way I found the difference was by auditing the actual diff against it afterwards.

## 3. Subagent value

The boundary that mattered most in Task 2 was between SA-1 and SA-2, because both had `services/users.py` as their Output in `DECOMPOSITION.md`. SA-1 added the `notification_pref` field, `NOTIFICATION_PREFS` and `DEFAULT_NOTIFICATION_PREF`, and SA-2 then added `list_users()`, `get_notification_pref()` and `set_notification_pref()` to the same file. Since the file was already modified when SA-2 started, `git status` could not show whether SA-2 had changed SA-1's work, so I amended the SA-2 prompt to record `git diff -- services/users.py` before and after its edits. The comparison showed the uncommitted diff going from 11 insertions and 3 deletions to 57 insertions and 3 deletions, with the three functions appended and every SA-1 line still there. Running each subagent in its own session helped too. SA-2 could not rely on anything it remembered from SA-1, so its prompt had a precondition check that the constants and field existed, and that check is what made the hand-off explicit. If I had let Claude implement the whole feature in one session, I would have had a single diff of `services/users.py` with data and service changes mixed together, no point at which the data layer was verified on its own (119 passed after SA-1), and no evidence about which step introduced a problem if one had appeared. No boundary was actually violated in this run, but this was the one where a violation would have been hardest to see.

## 4. Gap analysis

The constraint I would most want enforced mechanically is the file boundary in each subagent's Constraint field: a subagent may only modify the files in its Output field, inside this repository. In this run that rule existed only as text in the prompts. It held, but it was not guaranteed. The SA-1 session started in `C:\Users\Lokes` instead of the repository, found three copies of the project, and chose the right one by inspecting them, and nothing would have stopped it from editing a different copy. In the same way, SA-4 was told not to touch `services/users.py` or `routes/api.py` even if a test failed, and the only thing enforcing that was the sentence in its prompt. A hook should reject any Edit or Write call whose target path is outside the repository root or is not on the allowed-output list for the current subagent, for example anything other than `tests/test_users.py` and `tests/test_api.py` during SA-4.
