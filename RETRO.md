# Retro: COMP 4600/5300 PA 5

The clearest case of a Plan Mode amendment preventing an unwanted change is Session 1 in `PLAN_LOG.md`. The original plan (`plans/session1-original-plan.md`) added a `restore_tasks` fixture but limited it to "the new tests that call `create_task`", which would have left the new read-only test `test_seed_tasks_have_default_priority` as the one new priority test outside the shared-state fixture, with the restore placed after a bare `yield`. I amended the plan during Plan Mode review: all four new priority tests request `restore_tasks`, and the fixture restores `TASKS` inside a `finally` block (`plans/session1-amended-plan.md`). A diff of the two plan files shows exactly that change, and their SHA-256 hashes still match the ones recorded in the log. This example has two limits. The unwanted change was stopped at the plan stage, so it was never implemented and I have no failing test run that shows any harm. The amendment is also about consistency and not full isolation: the fixture restores `TASKS` after a test and does not reset it beforehand, and the amended plan itself notes that it does not isolate the six existing tests from each other. What the evidence shows is that an inconsistency in how the new tests treated shared state was visible in the plan and was removed there. If the original plan had been implemented, bringing that test under the fixture later would have meant reopening and re-verifying test code that was already written; because the change was made in the plan, no revert or rework happened.

The one case where the output did not fully match an amended plan is Session 1 in `PLAN_LOG.md`, which is marked "Partially". The amended plan (`plans/session1-amended-plan.md`) described `test_create_task_default_priority` as "omitted priority -> 3; other fields and next ID as before", and my prompt said to "implement only the approved changes", but the implemented test also contains `assert TASKS[expected_id] is result` (`tests/test_tasks.py`, committed in `246b401`), an identity check the plan never listed. The assertion is compatible with the intended behaviour, and the amendment itself was followed exactly: all four new priority tests use `restore_tasks` and the fixture restores in a `finally` block. What makes the case useful is how it surfaced. Claude's first summary after implementing said "There are no divergences from the approved plan" and mentioned the assertion only under "Beyond the plan's wording"; it was listed as a deviation only when I asked for a second comparison reporting "any deviations, including small ones". The reliability boundary this shows is that Plan Mode fixes what Claude intends before it edits, but it does not guarantee that the output contains only what the plan lists, and Claude's own end-of-session summary is not a reliable detector of small additions. A later comparison of plan text against committed code found that Sessions 2, 3 and 4 matched, so the evidence is one small addition in four sessions and not a pattern of drift; the practical lesson is to compare the result with the plan line by line instead of accepting "implemented as approved".

The most important boundary in Task 2 was that Subagent C could write `tests/test_notifications.py` but could not modify `services/users.py` or `routes/api.py`, and was told not to weaken, skip or delete a test to get a green run. The session transcripts show the write boundaries held for all three subagents: A changed only `services/users.py`, B changed only `routes/api.py`, C created only the test file, each wrote one handoff under `handoffs/`, and the prompt each received is byte-identical to its block in `DECOMPOSITION.md`. The boundary that did not hold exactly was the Input field. Each prompt said to read two named sections of `DECOMPOSITION.md`, and all three subagents read the whole file, including the other subagents' prompts; A and B also never opened `tests/test_tasks.py`, which their prompts listed under READ FIRST as a reference. Nothing broke as a result, and the handoffs (`handoffs/subagent-a-service.md`, `handoffs/subagent-b-api.md`) matched the agreed contract, so C's 56 cases passed on the first run and the planned path for a defect C could not fix was never used. If the whole feature had been implemented in one session, the tests would have been written by the same context that had just written the service and the routes, with nothing stopping it from adjusting either side until they agreed. I did not run that experiment, so this is a judgement and not a result, but Task 1 Session 1 shows the risk on a small scale: the session that wrote both code and tests summarised its own work as having no divergences when it had added something. The split does not make C blind to the implementation, since C was allowed to read it; what it adds is that C's expectations came from the contract and C could not change the code to fit them.

The Task 2 constraint I would most want enforced mechanically is the file boundary in Prompt C of `DECOMPOSITION.md`. Its "FILES YOU MAY MODIFY" list names only `tests/test_notifications.py` and `handoffs/subagent-c-tests.md`, and its "FILES YOU MUST NOT MODIFY" list names `tests/test_tasks.py`, `services/users.py`, `services/tasks.py`, `routes/api.py`, `app.py`, `utils/errors.py` and "every other file". A hook that enforces it would run before every file-editing tool call in the Subagent C session and block any call whose resolved path is not one of those two allowed files. In Task 2 that constraint was only text in a prompt. It held, but it was never tested, because all 56 new cases passed on the first run and C never had a reason to touch the implementation; the moment it matters is a failing test, which is also the moment an agent is most tempted to edit the code under test. The transcripts also show what such a hook would have to cover. Subagent A wrote `services/users.py` with a shell command (`cat > services/users.py`) and not with the Edit or Write tool, which was inside A's boundary but means a hook that inspects only file-editing tools would not have seen that write at all. The repository does contain a PreToolUse hook (`.claude/hooks/protect_paths.py`), but it protects `utils/errors.py`, `requirements.txt`, `PLAN_LOG.md`, `plans/` and `handoffs/`; it does not enforce this per-subagent constraint and does not inspect shell commands, so the constraint above is still advisory.
