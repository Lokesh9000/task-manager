# Retro: COMP 4600/5300 PA 5

The clearest case of a Plan Mode amendment preventing an unwanted change is Session 1 in `PLAN_LOG.md`. The original plan (`plans/session1-original-plan.md`) added a `restore_tasks` fixture but limited it to "the new tests that call `create_task`", which would have left the new read-only test `test_seed_tasks_have_default_priority` as the one new priority test outside the shared-state fixture, with the restore placed after a bare `yield`. I amended the plan during Plan Mode review: all four new priority tests request `restore_tasks`, and the fixture restores `TASKS` inside a `finally` block (`plans/session1-amended-plan.md`). A diff of the two plan files shows exactly that change, and their SHA-256 hashes still match the ones recorded in the log. This example has two limits. The unwanted change was stopped at the plan stage, so it was never implemented and I have no failing test run that shows any harm. The amendment is also about consistency and not full isolation: the fixture restores `TASKS` after a test and does not reset it beforehand, and the amended plan itself notes that it does not isolate the six existing tests from each other. What the evidence shows is that an inconsistency in how the new tests treated shared state was visible in the plan and was removed there.

Task 1 produced no divergence from an amended plan. `PLAN_LOG.md` records four Plan Mode sessions, two of them amended (Sessions 1 and 3), and all four are marked "Yes" for output matching the plan; Sessions 3 and 4 state "No genuine implementation divergence occurred", and Session 1 lists only minor deviations such as one extra identity assertion in `test_create_task_default_priority`, none of which changed the planned behaviour. I am not going to present one of those as a divergence, because it was not one. What this result means is narrower than "Plan Mode keeps the implementation on plan". The match was judged in the same sessions that wrote the code, and the per-session test counts (19, 31, 67 and 127) are reported in the log and were not re-run afterwards; only the plan files, their hashes and the final 127 passing tests were checked independently later. The plans for Sessions 3 and 4 also contained the function bodies almost verbatim, so there was little room for the output to drift. The evidence therefore shows that amendments were made and followed in four small, tightly specified sessions; it does not show how Plan Mode behaves when an implementation does drift, because that case never occurred.

The most important boundary in Task 2 was that Subagent C could write tests but could not edit `services/users.py` or `routes/api.py`, and was told not to weaken, skip or delete a test to get a green run. That rule is what makes the tests independent evidence: they were written against the "Agreed contract" in `DECOMPOSITION.md`, not adjusted to whatever A and B had produced. `handoffs/subagent-c-tests.md` reports 56 new cases (31 service level, 25 API level), `183 passed`, and "No defects or gaps found", and final verification confirmed that `tests/test_tasks.py`, `services/tasks.py`, `app.py` and `utils/errors.py` had no diff and that the changed files were exactly the union of the three allowed sets. Two limits apply. First, the boundary was never put under pressure: all 56 cases passed on the first run, so the planned path for a defect C could not fix was never used and I cannot say how well it would have held. Second, the boundaries of A and B rest on their own handoffs (`handoffs/subagent-a-service.md` and `handoffs/subagent-b-api.md`, each stating that only its one code file was modified) plus a diff that is consistent with them; `DECOMPOSITION.md` and `handoffs/` were untracked while the subagents ran, so Git cannot prove which session made which edit, and whether A and B received their prompts verbatim could not be checked afterwards.

The mechanically enforced rule is a project-level `PreToolUse` hook in `.claude/settings.json` that runs `.claude/hooks/protect_paths.py` before every Edit, Write and NotebookEdit call and exits with code 2, which blocks the call, when the resolved target is `utils/errors.py`, `requirements.txt`, `PLAN_LOG.md`, or anything under `plans/` or `handoffs/`. It was tested at two levels after it was installed. At script level, `python .claude/hooks/check_protect_paths.py` sends 32 tool calls to the script and all 32 behaved as expected: protected paths were blocked when written as relative paths, absolute paths, traversal such as `services/../utils/errors.py`, upper case, a trailing dot and an alternate data stream, while `services/tasks.py`, `CLAUDE.md`, `DECOMPOSITION.md`, `RETRO.md` and look-alike names such as `utils/errors.py.bak` were allowed. For the live test, a fresh headless Claude Code session (2.1.296) was asked to insert a comment as the first line of `utils/errors.py`; its Edit call returned "PreToolUse:Edit hook error ... protect_paths: blocked Edit on ... 'utils/errors.py' is a protected path in this project", and afterwards the file's SHA-256 was still `543040721ff2278f3a788face60d451c12e4ba56f2b75861bffe11c3a7298861` and `git diff -- utils/errors.py` was empty. The hook has real limits: it does not inspect Bash or PowerShell commands, so a shell redirect into a protected file is not blocked and remains a written rule in `CLAUDE.md` only; it was not confirmed to be active in the session that created it, which is why the live test used a fresh session; and it does not protect its own script or settings file.
